## 6.2 四类融合不能混为一谈

| 类型 | 例子 | 主要节省 | nano-vLLM 对应 |
|---|---|---|---|
| 权重打包/多输出 GEMM | gate 和 up 合为一次 linear | 一次 launch、一次输入读取 | `MergedColumnParallelLinear` |
| 逐元素 Kernel 融合 | `SiLU(gate) * up` 在一个 Kernel 完成 | 中间激活写入/读回、一次 launch | `SiluAndMul` |
| GEMM epilogue 融合 | GEMM tile 完成后直接激活并写回 | 整块 GEMM 输出的写回/读回 | 进阶目标，不是当前基线 |
| 图级融合/重放 | CUDA Graph 重放多条 GPU 命令 | CPU 提交和调度开销 | Decode CUDA Graph |

这些优化可以叠加，但收益来源不同。CUDA Graph 不会消除中间 Tensor 的 HBM 往返，也不会改变数学运算量。

## 6.3 从 GPU 成本解释融合

一次 Kernel launch 包含 Python/PyTorch 派发、CUDA 命令提交、GPU block 调度、数据加载和 tail effect。对 Decode 的小 Tensor，这些固定成本可能接近甚至超过数学计算；对 Prefill 的大 Tensor，HBM 和计算吞吐通常更重要。

一个算子链若计算相同，融合的潜在收益主要是：

1. 去掉中间 Tensor 的 HBM 写回与再读取；
2. 少一次 Kernel launch；
3. 让数据在寄存器或 shared memory 中直接被下一步使用；
4. 减少 allocator 和依赖图节点。

代价是 Kernel 可能更复杂、寄存器压力更高、occupancy 下降、shape 专用性更强，也更难调试。

## 6.4 未融合的 SiLU×up

逻辑实现：

```python
gate, up = gate_up.chunk(2, dim=-1)
silu_gate = torch.nn.functional.silu(gate)
out = silu_gate * up
```

`chunk` 通常只是两个 view。Eager 路径里典型地有两类点式 Kernel：

```text
SiLU Kernel：读 gate，写中间 silu_gate
Mul Kernel：读 silu_gate 和 up，写 out
```

以 BF16、`T` 个 token、中间宽度 `I` 计算，元素数 `N=T×I`：

```text
SiLU 读 gate          N
SiLU 写中间           N
Mul 读中间            N
Mul 读 up             N
Mul 写 out            N
合计                  5N 个元素
bytes_unfused = 5 × T×I × bytes_per_element
```

## 6.5 融合后的 SiLU×up

一个融合 Kernel 对每个 `(token, feature)` 读 gate 和 up，算出结果后直接写入输出：

```text
读 gate               N
读 up                 N
写 out                N
合计                  3N 个元素
```

因此：

```text
bytes_fused = 3 × T×I × bytes_per_element
saved       = 2 × T×I × bytes_per_element
saved_ratio = 40%
```

“40%”只描述这一小段激活的最低元素流量，不是整个 MLP 或端到端模型减少 40%。

## 6.6 Qwen3 的实际字节账

取 `I=3072`、BF16。

Decode batch `T=32`：

```text
N = 32 × 3072 = 98,304
未融合：5 × 98,304 × 2 = 983,040 B
融合：  3 × 98,304 × 2 = 589,824 B
每层节省：393,216 B = 0.375 MiB
28 层每 step 节省：10.5 MiB
```

同一层 gate_up 权重读取约：

```text
6144 × 1024 × 2 = 12 MiB
```

因此 Decode 端到端仍受权重读取和 GEMM 效率影响。融合有用，但不能把 10.5 MiB 的节省夸大成模型总流量减少 40%。

Prefill `T=512`：

```text
每层节省 = 2 × 512 × 3072 × 2 = 6 MiB
28 层合计 = 168 MiB
```

此时激活流量占比更高，但仍要与 QKV、Attention、gate/up GEMM 和 down GEMM 的时间比较。

## 6.7 nano-vLLM 做的是哪一步

当前 Qwen3 路径可以抽象为：

```text
Kernel A: x @ W_gate_up.T -> gate_up [T,6144] 写入 HBM
Kernel B: 读 gate_up -> 写 SiLU(gate)*up [T,3072]
Kernel C: hidden @ W_down.T -> output [T,1024]
```

权重合并把两条独立 gate/up GEMM 变成 Kernel A 的一次调用，但 `gate_up` 仍会完整写入 HBM，再由激活读到。

进一步做 GEMM epilogue 融合，理想路径才是：

```text
GEMM tile 算出 gate/up
    -> 留在寄存器或 shared memory
    -> 直接 SiLU×up
    -> 只写 [T,3072] hidden
```

它比单独融合点式算子更难：需要匹配 Tensor Core tile、处理两段输出、管理寄存器压力、选择 grid，并兼容 Tensor Parallel 分片和低精度转换。因此学习顺序应是：

1. 合并 gate/up 权重；
2. 融合 `SiLU×up`；
3. 尝试 `bias + activation` epilogue；
4. 最后做 GEMM + SwiGLU 的复杂融合。

为建立第一手经验，`labs/triton_linear_relu.py` 用一个分块 `tl.dot` 实现 `Linear + bias + ReLU`：矩阵乘结果留在寄存器/累加器中，激活后直接写输出，不把完整 pre-activation Tensor 写回 HBM。`lab09_linear_relu_fusion.py` 将它和 cuBLAS + 两个 Eager 点式 Kernel 对比。教学 Kernel 未必比 cuBLAS 快，这恰好说明“epilogue 更少”只是必要条件，不是充分条件。

## 6.8 线性层的计算与访存

矩阵乘：

```text
[T,H] @ [H,I] -> [T,I]
FLOPs ≈ 2THI
最低元素流量 = TH + HI + TI
```

算术强度：

```text
AI ≈ 2THI / ((TH + HI + TI) × bytes_per_element)
```

`T` 很小时，`HI` 权重读取占主导；`T` 增大后 FLOPs 增长更快，GEMM 更容易进入计算密集区。因此 Prefill 和 Decode 需要不同的优化策略。

## 6.9 `torch.compile` 能做什么

```python
@torch.compile
def silu_mul(gate_up):
    gate, up = gate_up.chunk(2, -1)
    return torch.nn.functional.silu(gate) * up
```

TorchInductor 可能把 `sigmoid`、乘法和 store 合成一个点式 Kernel，但它不保证把 GEMM 也一起融合成单个自定义 Kernel。必须区分：

1. 图捕获成功；
2. 点式算子被融合；
3. GEMM epilogue 被融合；
4. 在你的 shape 和 dtype 上确实更快。

观察生成代码：

```bash
TORCH_LOGS=output_code \
python labs/05_fusion_benchmark.py --tokens 32 \
  --intermediate 3072 --dtype bfloat16 --no-triton
```

重点查找是否出现 fused pointwise Triton Kernel，以及是否生成了意外的 contiguous 或 dtype 转换。

不同 `T` 可能触发重新编译。把编译时间与稳态时间分开记录；必要时尝试 `dynamic=True`，但动态 Kernel 不一定比 shape 专用 Kernel 快。

## 6.10 手写 Triton 融合 Kernel

`labs/triton_silu_mul.py` 的核心逻辑：

```python
@triton.jit
def silu_mul_kernel(gate_ptr, up_ptr, out_ptr, n_elements,
                    BLOCK: tl.constexpr):
    offsets = tl.program_id(0) * BLOCK + tl.arange(0, BLOCK)
    mask = offsets < n_elements
    gate = tl.load(gate_ptr + offsets, mask=mask).to(tl.float32)
    up = tl.load(up_ptr + offsets, mask=mask).to(tl.float32)
    out = gate * tl.sigmoid(gate) * up
    tl.store(out_ptr + offsets, out, mask=mask)
```

它只融合激活和乘法，不包含 GEMM。每个输出元素独立计算，适合用 block 级 Triton 编程学习。

边界包括：

- mask 防止最后一个 block 越界；
- 在 FP32 中计算后写回 BF16；
- block 太小导致 launch 多，block 太大可能增加寄存器和占用率压力；
- 输入必须满足该简化 Kernel 的连续布局假设。

## 6.11 正确性验证

建立 FP32 reference：

```python
gate, up = gate_up.chunk(2, -1)
ref = torch.nn.functional.silu(gate.float()) * up.float()
actual_fp32 = actual.float()
torch.testing.assert_close(actual_fp32, ref, rtol=2e-2, atol=2e-2)
```

容差要按 dtype 调整。还应该测试：

- 非 block 整数倍的最后一维；
- 正数、负数和接近 0 的输入；
- 极小 `T`；
- 连续多次调用没有 stale output；
- CPU/GPU 或不同后端的结果一致到合理误差。

## 6.12 Benchmark 的基本结构

公平实验分成：

```text
初始化/编译 -> correctness -> warmup -> timed repeats -> profile
```

`labs/common.py` 使用 CUDA Event，warmup 后再计时，并在 end Event 后同步。热循环中不做 `empty_cache()`、同步打印或改变 batch。

输出至少记录：

```text
T, dtype, eager_ms, compiled_ms, triton_ms, max_error
```

并计算理论有效带宽：

```text
effective_bandwidth = bytes_moved / elapsed_seconds
```

对融合路径用 `3N×bytes`，对未融合路径用 `5N×bytes`。如果计算的带宽超过 GPU 理论带宽，先检查字节账、缓存、同步和计时。

## 6.13 如何看结果

对于固定 `I=3072` 的小 batch 激活链，通常可观察到：

- `T=1`：绝对时间很小，launch 和固定开销占比高；融合可能明显，也可能被测量噪声掩盖；
- `T=8/32`：少一次 Kernel 和少一次中间写回更容易体现；
- `T=128/512`：流量更大，融合的 HBM 收益更容易观察；
- 更大的 Tensor 可能接近带宽上限，但端到端倍数仍受其他算子影响。

这些是趋势，不是固定倍数。功耗、时钟、后台程序、dtype、Inductor 版本和 Kernel 布局都会改变结果。

必须同时看“激活 microbenchmark”和“完整 MLP / 请求”的结果。只测激活时，收益可能被夸大；只测端到端时，小收益可能被注意力和其他 GEMM 掩盖。

## 6.14 Profile 里应该找什么

使用 `torch.profiler`：

```python
with torch.profiler.profile(
    activities=[torch.profiler.ProfilerActivity.CUDA],
    record_shapes=True,
) as prof:
    for _ in range(10):
        out = fn(gate_up)
    torch.cuda.synchronize()

print(prof.key_averages().table(
    sort_by="self_cuda_time_total",
    row_limit=20,
))
```

重点观察：

- Kernel 名和调用次数；
- 原有两个点式 Kernel 是否变成一个；
- GEMM 是否仍是最大时间项；
- 中间 Tensor 的分配是否减少；
- 是否有隐式 contiguous 或 dtype 转换；
- `T` 变化时是否因重编译/新算法使 Kernel 名或耗时改变。

## 6.15 为什么融合后可能不变快

| 原因 | 解释 |
|---|---|
| 计算本来就受限 | 减少读写不能解决 Tensor Core/SFU 吞吐不足 |
| 寄存器压力上升 | occupancy 下降，延迟无法被隐藏 |
| 丢失 Kernel 间并行 | 原本可在不同 stream 并行的任务被串行化 |
| 小 shape 固定成本为主 | 少一个 launch 不一定改变大头 |
| 自定义布局不佳 | 手写 Triton 可能不如库实现 |
| 编译未预热/动态 shape | 重复编译污染测量 |
| 中间 Tensor 本来就在缓存 | 减少的访问部分命中 L2 |

所以优化时必须保留 baseline，并同时报告正确性、绝对耗时、理论流量和 Profiler 证据。

## 6.16 从 MLP 到引擎的优化阶梯

当前 Qwen3 MLP：

```text
gate_up GEMM -> SiLU×up 融合 -> down GEMM
```

可继续探索：

1. 合并 gate/up 权重；
2. 融合 SiLU×up；
3. 将 gate/up GEMM 与激活做成 epilogue；
4. 优化 Tensor Core tile 和 GEMV/GEMM 调度；
5. 叠加 KV Cache、Continuous Batching、CUDA Graph；
6. 最后才考虑量化或更激进的数据格式。

每次只改一层，并在 nano-vLLM 真实短请求上验证：微基准收益必须是端到端收益的必要证据，而不是替代证据。

## 6.17 常见错误

| 错误 | 后果 | 修正 |
|---|---|---|
| 融合前后算法不同 | 加速比无意义 | 数学、dtype、容差一致 |
| 把编译时间算入稳态 | 误判变慢 | 预热并单独报冷启动 |
| 每次 `empty_cache()` | allocator 反复工作 | 固定缓存条件 |
| 只测一次 | 噪声主导 | 多次重复并报 median/p90 |
| 忘记 mask | 越界读写 | 测试非整块 shape |
| 把 view 当复制 | 流量公式错误 | 查 `stride`/`data_ptr` |
| 用 `time.time` 测异步 Kernel | 测到提交而非执行 | CUDA Event |
| 只报倍数 | 无法判断 baseline | 同时报绝对值和形状 |
