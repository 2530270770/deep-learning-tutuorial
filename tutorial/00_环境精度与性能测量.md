## 0.2 先建立“计算账本”

推理优化不是先改 Kernel，而是先把问题写成数量关系：

```text
耗时 = 计算 / 有效算力
     与 访存 / 有效带宽
     与 Kernel launch
     与 CPU 调度和同步等待
     中较慢的那一组叠加
```

例如一个普通逐元素激活只读一个输入、写一个输出：

```text
输入 100 万个 BF16 元素 = 2,000,000 B
输出 100 万个 BF16 元素 = 2,000,000 B
总流量至少 4,000,000 B
```

若 GPU 的有效 HBM 带宽是 250 GB/s，则纯带宽时间下限约为：

```text
4,000,000 / 250,000,000,000 = 0.000016 s = 16 μs
```

如果实测是 25 μs，就不能先断言“数学函数太慢”；多出来的 9 μs 可能来自 launch、缓存未命中、Kernel 内利用率不足或测量误差。

每次实验都应记录下面的账本：

```text
输入输出形状 -> 元素数 -> dtype 字节数 -> 最低读写字节数
FLOPs       -> 算术强度 -> 更可能偏计算还是偏访存
Kernel 数   -> 是否有不必要的中间 HBM 往返
同步点      -> 是否把 CPU/GPU 串行化了
```

## 0.3 检查环境

在当前教程根目录运行：

```bash
python environment_check.py
python -m unittest tests/test_math_reference.py
```

脚本输出会随硬件和依赖不同而变化，但关键字段应满足：

```text
Python                     3.11.x
PyTorch                    2.6.0+cu124
CUDA available             True
CUDA runtime              12.4
GPU                        NVIDIA GeForce RTX 3060 Laptop GPU
Compute capability         (8, 6)

```

`torch.version.cuda` 是 PyTorch 编译时使用的 CUDA runtime，不是系统 `nvcc --version`。它们不必字符串完全相同，但驱动必须足够新，且 `torch.cuda.is_available()` 必须为真。

### 常见错误

| 症状 | 常见原因 | 检查 |
|---|---|---|
| `torch.cuda.is_available() == False` | Windows Python、WSL 未启用 GPU、驱动问题 | 在 WSL 运行 `nvidia-smi` |
| CUDA out of memory | 模型之外还有旧进程、KV Cache 估值过高 | `nvidia-smi`，降低 `max_model_len` 和利用率 |
| FlashAttention 编译失败 | CUDA toolkit、编译器或 PyTorch ABI 不匹配 | 先确认版本，再看看能否用预编译 wheel |
| 用系统 Python 后库全丢 | 未激活 conda/venv | `which python`、`python -c "import sys; print(sys.executable)"` |
| 同一段代码一会快一会慢 | 首次编译、时钟变化、后台程序 | 固定预热、重复次数和电源模式 |

## 0.4 FP32、FP16、BF16

| dtype | 总位数 | 指数位 | 尾数位 | 动态范围 | 对本教程的意义 |
|---|---:|---:|---:|---|---|
| FP32 | 32 | 8 | 23 | 很大 | 数值验证和参数统计基线 |
| FP16 | 16 | 5 | 10 | 较窄 | 接近 65504 后可能溢出 |
| BF16 | 16 | 8 | 7 | 与 FP32 类似 | Qwen3 推理首选，Tensor Core 支持好 |

BF16 不是“更精确的 FP16”。它牺牲尾数精度换动态范围。对语言模型权重和激活，这通常比 FP16 更稳；但计算误差仍可能影响数值比较。

下面的验证使用 65504 附近的值：

```python
import torch

x = torch.tensor([60000.0, 65504.0, 65520.0])
print(x.to(torch.float16))
print(x.to(torch.bfloat16))
```

预期现象：

- FP16 在 65520 附近可能变成 `inf`；
- BF16 可表示约 6 万，但相邻可表示数更稀疏，量化误差较大。

比较浮点结果时不要用 `==`：

```python
torch.testing.assert_close(actual, expected, rtol=1e-2, atol=1e-2)
```

BF16 的容差通常比 FP32 宽，但应先建立 FP32 reference，再验证低精度实现。

### 常见错误

- 在 CPU 上创建 BF16 后惊讶于算得慢：BF16 CPU Kernel 支持因版本和平台而异，数值正确不代表性能有意义。
- 在小样本上用极宽容差让错误实现通过：正确性测试必须有明确容差和边界值。
- 把权重 dtype 改了，却没改输入或输出，触发 dtype 不一致。
- 认为 BF16 永远更快：带宽和 Tensor Core 利用不足时，编译开销或不支持的算子在短期内可能更慢。

## 0.5 GPU 异步执行与正确计时

PyTorch 调用 CUDA Kernel 通常是异步的：

```python
start = time.perf_counter()
y = x @ w
end = time.perf_counter()
```

这里 `end - start` 主要可能只测到 Python 和 launch 提交，而不是矩阵乘完成。正确方法是使用 CUDA Event：

```python
import torch

torch.cuda.synchronize()
start = torch.cuda.Event(enable_timing=True)
end = torch.cuda.Event(enable_timing=True)

for _ in range(10):        # warmup
    y = x @ w

start.record()
for _ in range(100):
    y = x @ w
end.record()
torch.cuda.synchronize()   # 等 end 真正完成

print(start.elapsed_time(end) / 100, "ms/call")
```

`common.py` 中的 `benchmark_cuda()` 就是这一模式。较大的重复次数可以减少计时噪声，但每轮都重新分配大张量会混入 allocator 行为，因此需保持实验一致。

### warmup 到底预热什么

首次调用可能包含：

- JIT/Kernel 选择；
- `torch.compile` 首次编译；
- Triton 编译缓存加载；
- cuBLAS/cuDNN 算法选择；
- CUDA context 初始化和显存池增长。

所以必须区分：

1. 冷启动总耗时；
2. 编译后首次调用；
3. 稳态 Kernel 时间；
4. 端到端请求延迟。

优化推理引擎时三者都需要，但不能把编译时间算进稳态吞吐，也不能用稳态结果掩盖用户第一次请求的卡顿。

## 0.6 显存测量

```python
torch.cuda.empty_cache()
torch.cuda.reset_peak_memory_stats()
base = torch.cuda.memory_allocated()

with torch.inference_mode():
    y = model(x)
torch.cuda.synchronize()

peak = torch.cuda.max_memory_allocated()
print("allocated peak delta (MiB):", (peak - base) / 2**20)
```

注意：

- `memory_allocated` 是 PyTorch allocator 已分配出去的量，不等于整张卡被占用的量；
- `nvidia-smi` 还包括 CUDA context、缓存和其他进程；
- `empty_cache()` 会释放未被引用的缓存，不应放在性能计时的热循环里；
- 输出张量如果没有释放，峰值会多算它。

## 0.7 Qwen3-0.6B 的初始安全配置

先用 Eager 模式验证正确性：

```python
llm = LLM(
    model_path,
    enforce_eager=True,
    max_model_len=1024,
    max_num_batched_tokens=256,
    max_num_seqs=8,
    gpu_memory_utilization=0.75,
)
```

小请求验证通过后，再逐渐增大长度或关闭 `enforce_eager`。生产配置不能直接搬到 6 GB 卡：

- `max_num_batched_tokens=16384` 只是调度上限，不代表设备一定放得下全部中间激活；
- `gpu_memory_utilization=0.9` 在高显存机器上常见，在 6 GB 笔记本卡上需要更保守；
- 模型参数约占 1.2 GB，但 KV Cache、临时 workspace、CUDA Graph 和碎片都会叠加。

一个上下文长度的 KV 粗略公式是：

```text
bytes = 2(K 和 V) × layers × context_tokens
        × kv_heads × head_dim × bytes_per_element
```

对于 Qwen3-0.6B、BF16、单卡 TP=1：

```text
每 token 的 KV = 2 × 28 × 8 × 128 × 2
               = 114,688 B
               ≈ 112 KiB
```

所以 1024 token 的 KV 理论上约 112 MiB。它不含 block 内部碎片、block table 和其他运行时缓冲。

## 0.9 常见错误总表

| 错误 | 结果 | 修正 |
|---|---|---|
| 忘记 `torch.cuda.synchronize()` | 测到的是异步提交时间 | 用 CUDA Event 并对 end 同步 |
| 每次计时都 `empty_cache()` | allocator 反复工作，结果失真 | warmup 后固定缓存条件 |
| 只运行一次 | 首次编译、时钟抖动污染结果 | 多次 warmup，固定重复数 |
| 形状每次变化 | `torch.compile` 反复重编译 | 分 shape 记录，聚合前先比较 |
| 只报加速比 | 无法判断 baseline 是否公平 | 同时报绝对时间、形状、dtype、带宽 |
| 只看平均值 | 尾延迟和抖动被掩盖 | 报 median、p90、最大值 |

## 0.12 与 nano-vLLM 的关联

nano-vLLM 启动时会读取 Hugging Face `config.json`，按配置初始化 Qwen3 权重和 KV Cache；`ModelRunner.allocate_kv_cache()` 还直接使用 `hf_config.dtype.itemsize` 估算 block 大小。因此本章的 dtype、设备、显存和 CUDA Event 知识，是后面判断 Scheduler 为什么分配失败、为什么 Decode 首步慢、以及 ncu/nsys 数据是否可信的前置条件。
